**How the mutation gates work now** (details: `docs/ENGINEERING_PROCESS.md`):
- Stryker's command is `node scripts/run-tests.js` (also `npm run test:src`): all `src/**/__tests__/*.test.js` in one process, sorted, stopping at the first failing file; a file passes/fails exactly as under `node --test` (tests: `scripts/__tests__/run-tests.test.js`, 11). **Convention:** `process.exit(...)` is a test file's last action and a file leaves no timers (the runner fails a file that does). `npm test` still uses `node --test` and also runs `scripts/__tests__/` (22 files in all).
- `mutation-full` (push to `main`): `scripts/mutation-full-skip.js` (rules in `src/utils/mutation-full-skip.js`) skips Stryker only if every changed file ends in `.md` **and** `mutation-full` concluded `success` on the push's `before` commit (Actions API, job `permissions: actions: read`). Anything else runs, including a crash or hang (> 2 min) of the decision step.
- `mutation-changed` diff step (PRs): `npm run mutate:changed -- "$BASE_REF" --concurrency 4` diffs against exactly `refs/remotes/origin/<base>` (`git show-ref --verify`, same as the ratchet step; a missing or option-like base fails with `::error::`). Changed files come from `git diff --name-status -z --find-renames`, then one `git diff -U0` per file reading only `@@` headers (`--no-textconv --text --inter-hunk-context=0`, literal pathspecs, `GIT_DIFF_OPTS` dropped), so file names, attributes, config and look-alike content can't drop or shift a range. Each file's absolute path is checked with Stryker's own minimatch (as its `FileMatcher` does) and fails with `::error::` if it can't match itself (glob syntax in the file or checkout folder name) or is a glob to Stryker's options check (`a?.js`). After the run, Stryker's `Found N of M file(s) to be mutated` must equal the changed files, or `::error::` (Stryker drops `.next`, `node_modules` in any case and `ignorePatterns` folders before matching; matching nothing gives no such line, score NaN, exit 0). Stryker's output is shown live and kept; only an "under breaking threshold" failure is reported as under 80% (spawn errors and signals are named). **Not guarded:** the generated config starts from the PR's own `stryker.config.json`, so a PR can still weaken its check there (`dryRunOnly`, `mutator.excludedMutations`, …; reproduced: `dryRunOnly: true` → `Found 1`, no mutants, exit 0), as can pass-through args (`--mutate`, `--dryRunOnly`); see the Open TODO "The ratchet checks only `thresholds.break`". ## How the Pattern Scanners Work (copy this shape for crypto / async)

Each scanner in `src/scanner/patterns/` exports `async scanForX(targetPath)` returning findings matching the schema in PRD.md §3:

1. `walkDir(targetPath)` returns files already filtered by `shouldSkipFile` (target-relative; `{ includeTests: true }` to keep `.test.`/`.spec.` files) → skip non-`isSourceFile` files
2. `toStatements(lines)` → iterate logical statements (multi-line safe); skip statements starting with `//` or `*`
3. `PATTERNS` array: `{ name, regex (global), sqlText/extractor, detected, description }`; reset `regex.lastIndex` before each use
4. Filter matches with a "does this really look like X" check (SQL: `looksLikeSql`) to keep false positives down
5. `assessContext(lines, statement, …)` → `{ factors, severity, confidence }`; look back `CONTEXT_WINDOW = 15` lines for user input / route handlers / mitigations; shift severity along `['low','medium','high','critical']`
6. Finding fields: `id`, `type` (`'xss'` for XSS — already counted in `index.js` coverage), `title`, `severity`, `confidence` (0.1–0.95), `description`, `file`, `line` (1-based statement start), `snippet` (whitespace-collapsed, ≤120 chars), `context` (3+ factors, ✓/⚠/? prefixes), `remediation` (actionable, with example), `references` (OWASP), `tags`
7. Wire into `src/scanner/pattern-scanner.js` inside its own try/catch

Tests: plain Node scripts (no framework), run with `node src/scanner/__tests__/<name>.test.js`; each writes fixtures to a tmp dir, prints ✓/✗, exits non-zero on failure. Note `.test.`/`.spec.` files are skipped by the walker (except for the secrets scanner, provider formats only), so SQLi/XSS fixtures must use other names.

## Questions to Ask Before Starting

1. **Is the core loop (scanner → JSON → dashboard) intact?** (Should always be yes)
2. **Can I explain this in 3 minutes to an interviewer?** (Check before shipping)
3. **Is the code clean + understandable?** (No hacky workarounds)
4. **Did I test the happy path AND the unhappy path?** (Edge cases matter)
5. **Am I on pace for the timeline?** (Week 1 = scanner, Week 2 = dashboard, Week 3 = deploy)

If any is "no," flag it. That's what the TPM is for.
